## The real dataset

Everything so far ran on small made-up inputs. The capstone uses the real thing: <Term>MNIST</Term>, 70,000 handwritten digits written by US Census Bureau employees and high-school students, collected by NIST and turned into MNIST in the 1990s. By the end of this module, a network built entirely from your own library will read them.

The dataset is four files:

| File | What's in it | Size in bytes |
| --- | --- | --- |
| `train-images-idx3-ubyte` | 60,000 training images, 28 × 28 pixels each | 47,040,016 |
| `train-labels-idx1-ubyte` | the digit (0–9) each training image shows | 60,008 |
| `t10k-images-idx3-ubyte` | 10,000 test images | 7,840,016 |
| `t10k-labels-idx1-ubyte` | their labels | 10,008 |

These aren't images you could open, and they aren't CSV or JSON. They're raw bytes in a simple format called **IDX**, and before you can train on them you need to read them. That's this lesson.

## Bytes and big-endian numbers

A file is a sequence of <Term>byte</Term>s, each a whole number from 0 to 255. A pixel fits in one byte (0 is blank paper, 255 is full ink), and so does a label. But the file also has to record how many images it holds. 60,000 doesn't fit in one byte, so IDX stores sizes as four bytes each: an unsigned 32-bit integer.

Read four bytes $b_0, b_1, b_2, b_3$ as the digits of a number in base 256:

$$
n = b_0 \cdot 256^3 + b_1 \cdot 256^2 + b_2 \cdot 256 + b_3
$$

Putting the most significant byte first, the way we write decimal numbers, is called <Term t="big-endian">big-endian</Term>. Most CPUs today store integers the other way round (little-endian), so a file format has to say which order it uses. Reinterpreting the bytes directly in memory would give the wrong number on your machine.

## The IDX header

Every IDX file starts with a header that describes the data that follows:

```text
bytes 0, 1    0, 0         always zero
byte  2       0x08         the data type: 8 means unsigned bytes
byte  3       d            the number of dimensions
next 4·d      the sizes    one big-endian u32 per dimension
the rest      the data     (product of the sizes) bytes, last dimension fastest
```

The training images file starts `0 0 8 3`, then the sizes 60,000, 28 and 28, then 47,040,000 pixel bytes. The labels file starts `0 0 8 1`, then 60,000, then one byte per label.

Those first four bytes are a <Term t="magic number">magic number</Term>: a fixed signature identifying the file type. MNIST is distributed gzip-compressed, and a compressed file starts with the bytes `0x1f 0x8b` instead. If you forget to decompress, the magic check gives you a clear error instead of 47 million bytes of garbage.

The header also tells you exactly how long the file must be: $4 + 4d + \prod_i \text{size}_i$ bytes. Checking that catches a truncated download before it turns into a mysterious crash halfway through training.

<Callout type="lang">

<Lang only="python">

All 60,000 training images are 47 million pixels. As a list of lists of Python floats, each number costs about 32 bytes (the float object plus a pointer to it), so the whole set would need around 1.5 GB of memory, and one epoch over it in pure Python would take about 20 minutes. That's why the Python track trains on a slice of 5,000 images (about 125 MB). You'll still get above 90% accuracy.

</Lang>
<Lang only={["rust", "cpp"]}>

All 60,000 training images are 47 million pixels, which comes to 376 MB as 64-bit floats. That fits comfortably, and compiled code is fast enough to train on all of them in well under a minute per epoch.

</Lang>

</Callout>

<KeyIdea>

A file is just bytes. IDX describes its own layout: a magic number (0, 0, type, number of dimensions), one big-endian 32-bit size per dimension, then the data. Validating the header and the length up front turns a corrupt file into a clear error.

</KeyIdea>
