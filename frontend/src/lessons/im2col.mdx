## Loops are slow

Your `conv2d` is four nested loops (six with channels). It's correct, but slow: every iteration does one multiply-add with lots of index arithmetic around it. Meanwhile, **matrix multiplication** is the most heavily optimized operation in computing. Libraries like BLAS and every GPU are built to do it fast, using cache blocking, vector instructions and thousands of parallel cores.

So the trick real frameworks use is to **rewrite convolution as a matrix multiplication**.

## Patches become rows

<Term>im2col</Term> ("image to columns") copies every patch the kernel would visit into one row of a big matrix. With a $k\times k$ kernel, each row has $k^2$ numbers, and there's one row per output position:

<Im2colViz />

Now every output is a row of that matrix dotted with the flattened kernel, and all of them together are a single matrix-vector product:

$$
\text{out} = \texttt{reshape}\big(\texttt{im2col}(X)\;\texttt{flatten}(K)\big)
$$

With many filters, stack the flattened filters as the columns of a matrix, and the whole layer becomes **one matrix-matrix product**. With channels, each row holds the patch from every input channel ($C \cdot k \cdot k$ numbers).

## The price

im2col copies each pixel up to $k^2$ times (once for every patch that contains it), so it uses much more memory than the image itself. A 3×3 convolution's patch matrix is about 9 times larger than its input. That's usually a good trade, because memory is cheaper than time, and it's the approach behind classic deep-learning libraries. (Newer ones use cleverer variants like Winograd transforms or fused GPU kernels, but the idea is the same.)

<KeyIdea>

im2col unrolls every patch into a row, so a convolution becomes a matrix product with the flattened kernels, the operation hardware is best at. The cost is memory: each pixel is copied up to $k^2$ times.

</KeyIdea>
